# CareLink 目录结构与分层规则

提案第 2 章承诺了两件事，目录结构必须同时体现出来：

1. **按特性分包**（package-by-feature）——技术栈表原话："Feature modules with `api`, `application`, `domain`, and `infrastructure`"
2. **四层依赖朝内**——"表现层、应用层、领域层、持久化层，每一层只依赖它下面的那一层"，且"领域层可以脱离运行中的应用与数据库单独做单元测试"

所以是**外层按业务切、内层按技术分层**：五个业务模块并列，每个模块内部各有自己的四层。

### 每一层允许做什么

| 层 | 放什么 | **不许**放什么 |
|---|---|---|
| `api` | 控制器、DTO、参数格式校验、HTTP 状态码 | 任何业务规则、任何 SQL |
| `application` | 编排用例步骤、开事务、调领域对象 | 业务规则本身（那是领域层的） |
| `domain` | 实体、值对象、领域服务、仓储**接口**、五个设计模式 | Spring 注解（尽量）、JPA 注解、任何 import 上面两层 |
| `infrastructure` | JPA 实体映射、仓储**实现**、外部服务适配器 | 业务规则 |

**领域层是重点。** 五个设计问题全部住在 `domain/` 里，报告 3.4 的四张图画的也是这一层。领域层不依赖 Spring 与数据库，是它能"用纯 JUnit 毫秒级跑完"的前提——这条写进了提案的非功能需求。

### 模块之间怎么调

- **禁止**跨模块直接 import 对方的 `domain` 或 `infrastructure`
- 需要别人的能力时，调对方 `application` 层暴露的接口
- 例：M2 排班要判断资质是否有效 → 调 `careplan.application.CertificationQuery`，不去碰 `careplan.domain`

## 二、前端

前端不是"四个应用"，是**一套 React 代码服务四个角色**（提案第 2 章原话）。所以也分两个维度：**功能按模块切、页面按角色切**。

```
frontend/
├─ package.json
├─ vite.config.ts
└─ src/
   ├─ main.tsx
   ├─ App.tsx                          路由表与角色分流
   │
   ├─ shared/                          跨角色共用
   │  ├─ api/                          API 客户端，按后端模块分文件
   │  │  ├─ client.ts                  axios 实例、拦截器、错误处理
   │  │  ├─ careplan.ts
   │  │  ├─ roster.ts
   │  │  ├─ visit.ts
   │  │  ├─ incident.ts
   │  │  └─ report.ts
   │  ├─ components/                   通用组件：按钮、表单、表格、空状态
   │  ├─ theme/
   │  │  ├─ standard.ts                主管、护理员、家属用
   │  │  └─ elder.ts                   老人端：大字号、高对比、大点击区
   │  ├─ hooks/
   │  └─ auth/                         登录、角色上下文、路由守卫
   │
   ├─ features/                        ← 与后端模块一一对应，一人一个
   │  ├─ careplan/                     M1：计划树组件、工时汇总展示
   │  ├─ roster/                       M2：排班网格、候选与理由
   │  ├─ visit/                        M3：打卡、任务清单、体征录入
   │  ├─ incident/                     M4：异常工作台、SOS 按钮
   │  └─ report/                       M5：周报视图、体征趋势图
   │
   └─ routes/                          ← 按角色组装页面
      ├─ manager/                      桌面布局，信息密度高
      ├─ caregiver/                    移动优先
      ├─ family/                       移动优先
      └─ elder/                        大按钮、图标化
```

**分工落到文件上**：每个人写自己 `features/<模块>/` 下的组件与 `shared/api/<模块>.ts`，然后在 `routes/<角色>/` 下摆自己的页面文件。四个角色目录里会有多个人的文件，但**文件不重叠**（`manager/CarePlanPage.tsx` 是 M1 的，`manager/RosterPage.tsx` 是 M2 的），不会冲突。

> 注：草稿阶段各自画各自的 UI 即可，不必先统一。等统一风格后重做时，`shared/components/` 与 `shared/theme/` 才成为约束。

## 三、用一个测试把分层焊死

提案的非功能需求里承诺了："**构建时的架构测试：领域层若引用表现层或持久化实现，构建失败**"。

用 ArchUnit 实现，放 `backend/src/test/java/sg/nus/carelink/architecture/LayerDependencyTest.java`：

```java
package sg.nus.carelink.architecture;

import com.tngtech.archunit.core.importer.ImportOption;
import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;

@AnalyzeClasses(
        packages = "sg.nus.carelink",
        importOptions = ImportOption.DoNotIncludeTests.class)
class LayerDependencyTest {

    @ArchTest
    static final ArchRule 领域层不依赖表现层与持久化层 =
            noClasses().that().resideInAPackage("..domain..")
                    .should().dependOnClassesThat()
                    .resideInAnyPackage("..api..", "..infrastructure..");

    @ArchTest
    static final ArchRule 表现层不直接依赖持久化层 =
            noClasses().that().resideInAPackage("..api..")
                    .should().dependOnClassesThat()
                    .resideInAPackage("..infrastructure..");

    @ArchTest
    static final ArchRule 领域层不依赖_JPA =
            noClasses().that().resideInAPackage("..domain..")
                    .should().dependOnClassesThat()
                    .resideInAnyPackage("jakarta.persistence..", "org.springframework.data..");

    @ArchTest
    static final ArchRule 模块之间不跨界访问领域层 =
            noClasses().that().resideInAPackage("sg.nus.carelink.(*)..")
                    .should().dependOnClassesThat()
                    .resideInAPackage("sg.nus.carelink.(*).domain..")
                    .because("跨模块只能调对方 application 层暴露的接口");
}
```

pom 里加依赖：

```xml
<dependency>
  <groupId>com.tngtech.archunit</groupId>
  <artifactId>archunit-junit5</artifactId>
  <version>1.3.0</version>
  <scope>test</scope>
</dependency>
```

这个测试跑在**快速阶段**，秒级完成。有人违反分层，PR 直接红——比在代码评审里靠人眼看可靠得多。

> 最后那条「模块之间不跨界」规则的写法在不同 ArchUnit 版本上略有差异，
> 第一次跑如果报错，先只启用前三条，第四条等模块起来了再调。

## 四、接口该放在哪里

Java 分层项目最常见的错误，是给每个 Service 都配一套 `XxxService` + `XxxServiceImpl`。
**本项目不这么做**——只有一个实现、又没人跨模块调用的接口是纯仪式。
接口只在四种情况下出现，每一种都有硬理由：

| 用途 | 接口放哪 | 实现放哪 | 为什么必须是接口 |
|---|---|---|---|
| **仓储** | `domain/repository/` | `infrastructure/persistence/` | 依赖倒置。领域层声明「我需要能存取访视」，但不知道用的是 JPA。**这是领域层能脱离数据库做单元测试的唯一原因** |
| **设计模式的多态点** | `domain/model/` 或 `domain/service/` | 同包下多个实现类 | 五个设计问题本身就是「一个接口多种实现」：State、Strategy、Handler 都是 |
| **外部服务端口** | `domain/port/` | `infrastructure/adapter/` | 语言模型不可用时要换成规则实现，接口就是那个可替换点 |
| **跨模块契约** | `application/` | 同模块内的服务类 | 别的模块 import 这个接口而不是你的实现，你重构内部不会碰坏别人 |

**不需要接口的**：只有一个实现、也不被跨模块调用的应用服务，直接写类。
`CarePlanService` 就是个类，不必配 `CarePlanServiceImpl`。

> **为什么不沿用「每个 Service 配一个 Interface」的传统写法？**
>
> 那套写法当年是**技术强制**，不是设计品味：Spring 早期的事务代理只能用 JDK 动态代理，
> 而 JDK 动态代理**必须有接口**——没有接口，`@Transactional` 直接不生效。
> 加上 EJB 强制 Home/Remote 接口、早期 Mockito 不能 mock 具体类，才形成了 `Impl` 后缀的习惯。
>
> 这三条现在都没了：Spring Boot 2 起默认 CGLIB 类代理，具体类上的 `@Transactional` 正常工作；
> Mockito 5 的 inline mock maker 连 final 类都能 mock；EJB 早已退休。
> **习惯留下来了，原因没了。**
>
> （顺带：GoF 那句 "Program to an interface" 写于 1994 年，比 Java 还早一年，
> 指的是「依赖类型而非具体类」——类本身也是类型。它从未要求为每个类造一个孪生接口。）
>
> 1:1 接口的实际代价：方法签名写两遍、改动改两处；Ctrl+点击跳到接口看不到代码；
> **发出假信号**——读者看到接口会找「还有哪些实现」，答案是没有；且零解耦，改接口就是改实现。
>
> 对本项目还有一条更要紧的理由：报告 3.5 要每人论述一个设计问题与模式。
> **若每个 Service 都有接口，接口就不再携带信息**，评审分不清哪个是设计决策、哪个是样板。
> 按本规则，代码库里出现的每一个 `interface` 都是一次可辩护的设计决策。
>
> 注意差距没那么大：跨模块契约那条已经给了接口，
> **每个模块对外的服务照样有接口**，只有模块内部自用的服务才直接写类。
>
> 如果团队最终偏好传统写法，那就全员统一用传统写法——
> **一致性比这条偏好重要**，最糟的是五个人五种风格。

### 依赖倒置长什么样

```java
// domain/repository/VisitRepository.java —— 领域层只说「我需要什么」
public interface VisitRepository {
    Optional<Visit> findById(VisitId id);
    void save(Visit visit);
    List<Visit> findScheduledFor(CaregiverId caregiver, LocalDate date);
}
```

```java
// infrastructure/persistence/VisitRepositoryAdapter.java —— 持久化层去实现
@Repository
class VisitRepositoryAdapter implements VisitRepository {
    private final VisitJpaRepository jpa;
    private final VisitMapper mapper;
    // …把 JPA 实体翻译成领域模型
}
```

箭头方向是 `infrastructure → domain`，不是反过来。
所以领域层的单元测试可以直接 `new` 一个假的 `VisitRepository`，
**不启动 Spring、不连数据库、毫秒级跑完**——提案非功能需求里承诺的就是这件事。

### 端口与降级长什么样

```java
// domain/port/ClosureStructurer.java
public interface ClosureStructurer {
    ClosureRecord structure(String freeText);
}
```

两个实现放在 `infrastructure/adapter/`：`LlmClosureStructurer` 调模型服务，
`ManualClosureStructurer` 是降级。由配置决定注入哪个，模型挂掉自动切换。
**领域层完全不知道有没有语言模型这回事**——这就是"每一处 AI 都有规则降级"在代码上的落法。

## 五、给五个人的一句话

> 你的代码基本只出现在四个地方：
> `backend/.../<你的模块>/`、
> `backend/src/test/.../<你的模块>/`、
> `frontend/src/features/<你的模块>/`、
> `frontend/src/routes/<各角色>/<你的页面>.tsx`。
>
> 要碰 `shared/` 或改表结构，先在群里说一声。
