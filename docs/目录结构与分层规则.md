# CareLink 目录结构与分层规则

> **模块如何划分尚未敲定。** 本文只规定**每个模块内部**怎么分层、接口放哪里、
> 依赖朝哪个方向。这些规则与模块边界无关——无论最后按业务领域切还是按使用角色切，
> 四层结构都成立。模块定下来后照本文的骨架建包即可。
>
> 仓库里现有 `shared`（公共层）与 `identity`（认证，各模块共用）。
> **`identity` 就是四层写法的参照实现**，可以直接对着代码看。

提案第 2 章承诺了两件事，目录结构必须体现出来：

1. **按功能分包**（package-by-feature），不是按技术分包
2. **四层依赖朝内**——"表现层、应用层、领域层、持久化层，每一层只依赖它下面的那一层"，
   且"领域层可以脱离运行中的应用与数据库单独做单元测试"

所以是**外层按功能切、内层按技术分层**：功能模块并列，每个模块内部各有自己的四层。

## 一、后端骨架

```
backend/src/main/java/sg/nus/carelink/
├─ CareLinkApplication.java
│
├─ shared/                        跨模块共用，不属于任何功能模块
│  ├─ security/                   SecurityConfig、Role
│  ├─ error/                      BusinessRuleViolation、ResourceNotFound
│  │                              （纯 Java，领域层可以安全依赖）
│  ├─ web/                        GlobalExceptionHandler，统一 ProblemDetail
│  ├─ config/                     CareLinkProperties，业务阈值集中配置
│  ├─ audit/                      审计（待建）
│  └─ scheduling/                 定时任务框架（待建）
│
├─ identity/                      ← 参照实现，四层齐全
│  ├─ api/                        ① 表现层
│  ├─ application/                ② 应用层
│  ├─ domain/                     ③ 领域层
│  └─ infrastructure/             ④ 持久化层
│
└─ <功能模块>/                     模块边界确定后按同样骨架建
   ├─ api/
   ├─ application/
   ├─ domain/
   └─ infrastructure/
```

### 每一层允许做什么

| 层 | 放什么 | **不许**放什么 |
|---|---|---|
| `api` | 控制器、DTO、参数格式校验、HTTP 状态码 | 任何业务规则、任何 SQL |
| `application` | 编排用例步骤、开事务、调领域对象 | 业务规则本身（那是领域层的） |
| `domain` | 实体、值对象、领域服务、仓储**接口**、设计模式 | JPA 注解、Spring Data、任何 import 上面两层 |
| `infrastructure` | JPA 实体映射、仓储**实现**、外部服务适配器 | 业务规则 |

**领域层是重点。** 设计问题与设计模式都住在 `domain/` 里，报告 3.4 的四张图画的也是这一层。
领域层不依赖 Spring 与数据库，是它能"用纯 JUnit 毫秒级跑完"的前提。

### 模块之间怎么调

- **禁止**跨模块直接 import 对方的 `domain` 或 `infrastructure`
- 需要别人的能力时，调对方 `application` 层暴露的接口
- 例：`identity/application/UserDirectory` 就是这样一个对外契约

## 二、接口该放在哪里

Java 分层项目最常见的错误，是给每个 Service 都配一套 `XxxService` + `XxxServiceImpl`。
**本项目不这么做**——只有一个实现、又没人跨模块调用的接口是纯仪式。
接口只在四种情况下出现，每一种都有硬理由：

| 用途 | 接口放哪 | 实现放哪 | 为什么必须是接口 |
|---|---|---|---|
| **仓储** | `domain/repository/` | `infrastructure/persistence/` | 依赖倒置。领域层声明「我需要能存取什么」，但不知道用的是 JPA。**这是领域层能脱离数据库做单元测试的唯一原因** |
| **设计模式的多态点** | `domain/model/` 或 `domain/service/` | 同包下多个实现类 | 设计问题本身就是「一个接口多种实现」：State、Strategy、Handler 都是 |
| **外部服务端口** | `domain/port/` | `infrastructure/adapter/` | 语言模型不可用时要换成规则实现，接口就是那个可替换点 |
| **跨模块契约** | `application/` | 同模块内的服务类 | 别的模块 import 这个接口而不是你的实现，你重构内部不会碰坏别人 |

**不需要接口的**：只有一个实现、也不被跨模块调用的应用服务，直接写类。
仓库里 `IdentityService` 就是个类，没有配 `IdentityServiceImpl`。

> **为什么不沿用「每个 Service 配一个 Interface」的传统写法？**
>
> 那套写法当年是**技术强制**，不是设计品味：Spring 早期的事务代理只能用 JDK 动态代理，
> 而 JDK 动态代理**必须有接口**——没有接口，`@Transactional` 直接不生效。
> 加上 EJB 强制 Home/Remote 接口、早期 Mockito 不能 mock 具体类，才形成了 `Impl` 后缀的习惯。
>
> 这三条现在都没了：Spring Boot 2 起默认 CGLIB 类代理，具体类上的 `@Transactional` 正常工作；
> Mockito 5 的 inline mock maker 连 final 类都能 mock；EJB 早已退休。
> **习惯留下来了，原因没了。**
>
> （顺带：GoF 那句 "Program to an interface" 写于 1994 年，比 Java 还早一年，
> 指的是「依赖类型而非具体类」——类本身也是类型。它从未要求为每个类造一个孪生接口。）
>
> 1:1 接口的实际代价：方法签名写两遍、改动改两处；Ctrl+点击跳到接口看不到代码；
> **发出假信号**——读者看到接口会找「还有哪些实现」，答案是没有；且零解耦，改接口就是改实现。
>
> 对本项目还有一条更要紧的理由：报告 3.5 要每人论述一个设计问题与模式。
> **若每个 Service 都有接口，接口就不再携带信息**，评审分不清哪个是设计决策、哪个是样板。
> 按本规则，代码库里出现的每一个 `interface` 都是一次可辩护的设计决策。
>
> 如果团队最终偏好传统写法，那就全员统一用传统写法——
> **一致性比这条偏好重要**，最糟的是五个人五种风格。

## 三、参照实现：`identity` 模块

这是仓库里真实存在的代码，新模块照抄这个骨架。

```
identity/
├─ api/                                    ① 表现层
│  ├─ AuthController.java                  登录、当前用户；只管 HTTP 进出
│  └─ dto/
│     ├─ LoginRequest.java                 带 @NotBlank 的格式校验
│     └─ CurrentUserResponse.java          前端据 roles 决定进哪套界面
│
├─ application/                            ② 应用层
│  ├─ IdentityService.java                 类。没有 Impl，因为只有一个实现
│  ├─ UserDirectory.java             【接口】跨模块契约，别的模块只 import 这个
│  └─ UserDirectoryService.java            实现 UserDirectory
│
├─ domain/                                 ③ 领域层：纯 Java
│  ├─ model/
│  │  └─ AppUser.java                      不含密码散列——那是认证的实现细节
│  └─ repository/
│     └─ AppUserRepository.java      【接口】领域层声明需要什么
│
└─ infrastructure/                         ④ 持久化层
   ├─ persistence/
   │  ├─ AppUserJpaEntity.java             带 JPA 注解，与领域模型分开
   │  ├─ AppUserJpaRepository.java         Spring Data 接口，不向外暴露
   │  ├─ AppUserMapper.java                JPA 实体 → 领域模型，单向
   │  └─ AppUserRepositoryAdapter.java     实现领域层的 AppUserRepository
   └─ security/
      ├─ AuthenticationQuery.java    【接口】认证专用的窄读取端口
      ├─ JpaAuthenticationQuery.java       实现
      └─ JpaUserDetailsService.java        翻译成 Spring Security 的 UserDetails
```

### 依赖倒置长什么样

```java
// domain/repository/AppUserRepository.java —— 领域层只说「我需要什么」
public interface AppUserRepository {
    Optional<AppUser> findByUsername(String username);
    Optional<AppUser> findById(Long id);
}
```

```java
// infrastructure/persistence/AppUserRepositoryAdapter.java —— 持久化层去实现
@Repository
class AppUserRepositoryAdapter implements AppUserRepository {
    private final AppUserJpaRepository jpa;
    public Optional<AppUser> findByUsername(String username) {
        return jpa.findByUsername(username).map(AppUserMapper::toDomain);
    }
}
```

箭头方向是 `infrastructure → domain`，不是反过来。
所以测试里塞一个手写的假仓储就能跑通应用层——见
`src/test/.../identity/application/InMemoryAppUserRepository.java`，
**不启动 Spring、不连数据库、毫秒级跑完**。

### 一个值得注意的设计决定

`AppUser` 领域模型**刻意不含密码散列**：密码是认证机制的实现细节，
领域层只关心「这是谁、他能做什么」。认证需要散列时，走
`AuthenticationQuery` 这条独立的窄端口去取，领域模型因此保持干净。

同理，`shared/security/SecurityConfig` **不 import identity 的任何类**——
`UserDetailsService` 由 Spring 按类型注入。这让依赖方向保持 `identity → shared` 单向，
不产生模块间循环依赖（由下面的第四条规则强制）。

## 四、用一个测试把分层焊死

提案的非功能需求承诺了："**构建时的架构测试：领域层若引用表现层或持久化实现，构建失败**"。

`backend/src/test/java/sg/nus/carelink/architecture/LayerDependencyTest.java`（ArchUnit）四条规则：

| 规则 | 挡住什么 |
|---|---|
| 领域层不依赖 `..api..` 与 `..infrastructure..` | 依赖倒流，领域层被 Web/DB 绑架 |
| 表现层不直接依赖 `..infrastructure..` | 控制器绕过应用层直连仓储实现 |
| 领域层不依赖 `jakarta.persistence` 与 `org.springframework.data` | 领域模型被 JPA 污染，测试必须起数据库 |
| 模块切片之间无循环依赖 | 模块互相纠缠，最终退化成大泥球 |

这个测试跑在**快速阶段**，秒级完成。有人违反分层，PR 直接红——
比在代码评审里靠人眼看可靠得多。

## 五、前端骨架

前端不是"四个应用"，是**一套 React 代码服务四类角色**。所以也分两个维度：
**功能按模块切、页面按角色切**。

```
frontend/src/
├─ shared/                          跨角色共用
│  ├─ api/                          API 客户端，按后端模块分文件
│  ├─ components/                   通用组件
│  ├─ theme/
│  │  ├─ standard.ts                主管、护理员、家属用
│  │  └─ elder.ts                   老人端：大字号、高对比、大点击区
│  └─ auth/                         登录、角色上下文、路由守卫
│
├─ features/<模块>/                  与后端模块一一对应，一人一个
│
└─ routes/                          按角色组装页面
   ├─ manager/                      桌面布局，信息密度高
   ├─ caregiver/                    移动优先
   ├─ family/                       移动优先
   └─ elder/                        大按钮、图标化
```

**分工落到文件上**：每个人写自己 `features/<模块>/` 下的组件与 `shared/api/<模块>.ts`，
然后在 `routes/<角色>/` 下摆自己的页面文件。四个角色目录里会有多个人的文件，
但**文件不重叠**，不会冲突。

## 六、给团队的一句话

> 你的代码基本只出现在四个地方：
> `backend/.../<你的模块>/`、
> `backend/src/test/.../<你的模块>/`、
> `frontend/src/features/<你的模块>/`、
> `frontend/src/routes/<各角色>/<你的页面>.tsx`。
>
> 要碰 `shared/` 或改表结构，先在群里说一声。
